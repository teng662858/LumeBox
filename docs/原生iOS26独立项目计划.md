# LumeBox 原生 iOS 26 独立项目计划

**评审草案 v0.1 · 2026-11-12**
现有产品基线取自 `df02c312`。独立新项目、原生 iOS、最低系统 **iOS 26.0** 是本次确定的要求。下文的产品名称、首版范围、工期和性能目标均为评审建议。

## 1. 准备交付什么

建议把第一个可安装版本定义为一个完整的视频 App。用户在新安装的 iPhone 上接入现有私有订阅，选择一个源，找到一部剧，播放、换集、退出，再次进入时能从原进度继续。用这条路径同时检验原生界面、源兼容、网络、播放和数据保存。第二个交付版本加入漫画、图集、文字小说和有声书，之后分批补齐特殊源格式、离线和增强能力。

新应用采用独立 Git 仓库、Xcode 工程、Bundle ID、签名配置、容器和构建号。暂称“LumeBox Native”，正式名称可在建项时定。首轮按 iPhone、个人设备签名安装估算。两款 App 可以并排安装，旧版继续使用其 iOS 18 发布线。新项目的应用、项目自维护库、模拟器和设备构建统一以 iOS 26.0 为下限，在 iOS 26 和用户当前设备系统分别验证。

**何时可以替代旧版**取决于常用源、观看和阅读历史、后台音频及离线内容的验收。第一个能播放的安装包用于试用；待用户常用功能清单逐项通过，再切换日常使用。

## 2. 现有实现怎样影响工作量

| 现有资产 | 新项目处理方式 | 第一项需要证明的事情 |
| --- | --- | --- |
| UIKit 视频页、AVPlayer、libmpv 桥 | 在新库内拆出引擎与原生页面，去掉 Flutter 通道，保留已验证的切换和释放逻辑 | 已退出页面的回调不能覆盖当前集，MPV 的画面、水印及声音在真机方向正确 |
| Dart 视频会话、缓存及 HLS 处理 | 将媒体请求、分块转发、签名重取和进度保存的行为移植到 Swift，保留现有慢分片和 Range 样本 | 上游还在发后半段时，首批字节已经交给播放器 |
| LumeSource 脚本、源快照、私有订阅清单 | 沿用现有格式与脚本；为原生宿主实现网络、解析、加密、存储和超时接口 | 同一份发布脚本在两个 App 对固定响应给出等价结果 |
| QuickJS 原生代码、Node/Python 集成、FFmpeg 和模型 | 分别核对版本、许可证、设备架构、签名、包体和依赖。保留 QuickJS 中断能力；其他运行时按源格式分期接入 | 干净环境可重复构建，设备能中止超时任务，实际包体可测 |
| 漫画、小说、有声书的 Flutter 界面 | 把阅读位置、翻页、音频队列和无痕行为作为移植契约，在原生页面重新实现 | 同一本书在重启、旋转、改字号或接电话后能回到正确位置 |
| 现有 SQLite、配置备份、iCloud 和钥匙串 | 导入旧备份；新库独立写入。账号按新应用授权，云同步在冲突策略验证后开放 | 能预览、取消、重复导入和恢复失败前的状态 |
| 图像、朗读、网页验证、隐私等原生控制器 | 逐个剥离 Flutter 注册和回调；对照旧调用者检查输入、输出、错误和释放时机 | 退出页面后可取消任务，Cookie 和凭证只发给所属站点 |

当前视频实现以 AVPlayer、MPV 两个内核为基线。历史说明里的 MDK、Aether 和旧播放器面板不能直接计入首版功能。现有模拟器能证明两个内核的 MP4/HLS 基础路径，MPV 设备图形输出、扬声器、AirPlay 和实际画中画仍需逐项真机验收。详见[播放页重建记录](2026-11-12_原生视频播放页重建.md)。

## 3. 产品结构与分期范围

| 用户任务 | V0.1 视频试用 | V0.2 阅读试用及后续 |
| --- | --- | --- |
| 加入内容源 | 私有 GitHub 只读订阅、本地 LumeSource JS 导入、更新结果、启停、源设置、镜像选择和登录 | 批量订阅、历史版本回退、多文件包与其他格式逐类加入 |
| 找到内容 | 源选择、首页推荐、分类、分页、单源搜索、详情、线路和选集；保存最近使用源 | 跨源搜索、聚合去重、排序、高级筛选、TMDB/Bangumi 资料和进度同步 |
| 看视频 | AVPlayer/MPV、暂停、拖动、倍速、横竖屏、锁定、换线换集、续播、错误后重试；源要求时走网页播放 | 音轨和外挂字幕细化、画中画、AirPlay、基础与公共弹幕分开验证；片头片尾识别最后接入 |
| 看漫画和图集 | 先在数据模型保留内容类型 | 书架、章目录、连续滚动与分页、缩放、书签、进度、图片预取；图集复用图片浏览能力 |
| 读小说、听书 | 定义章节与音频内容契约 | 正文排版、字体主题、阅读定位；有声书后台、锁屏、倍速和定时；朗读与有声书共用音频占用策略 |
| 收藏与离线 | 收藏、逐集历史、无痕、清理缓存、旧备份预览及视频数据导入 | 完整跨板块迁移、下载中心、离线漫画、视频下载与封装、队列恢复、iCloud 同步 |
| 个性化与辅助能力 | 系统深浅色、动态字号、减少透明度、VoiceOver、隐私遮挡、诊断导出 | 字体导入、阅读布局、翻译、图像增强、离线模型及可选服务凭证管理 |

导航沿用用户熟悉的漫画／视频／设置结构。视频试用包只展示可完成的入口。阅读上线后，漫画入口承载漫画、图集、小说和有声内容，并在书架与详情显示内容类型。猫源入口可从视频源选择器打开，底层继续区分 `comic`、`video`、`cat` 的数据归属。设计评审看三条实机路径：从空库完成第一次播放、从历史续看、从书架继续阅读。

## 4. 原生工程和界面设计

建议使用 Swift、SwiftUI 和 UIKit，Xcode 应用目标负责装配，本地 Swift Package 按可独立测试的边界组织。列表、表单、设置和普通导航先用 SwiftUI。保留 UIKit 播放控制器，漫画缩放、长图复用和高频手势优先验证 UICollectionView／UIScrollView。使用系统导航栏、标签栏、菜单和 Sheet 获得 iOS 26 的交互与 Liquid Glass 外观。正文和字幕采用实底或稳定遮罩，横屏按钮避开安全区，辅助功能模式下检查对比度。参考 [Apple 的 Liquid Glass 采用指南](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)。

| 工程边界 | 职责和约束 |
| --- | --- |
| App、浏览与资料库 | 路由、来源切换、页面状态、可访问性。持久化作品身份采用板块、源、作品和章节的原始 ID |
| SourceRuntime | 将 `categories/list/detail/chapters/content` 和可选入口映射为有类型结果；保留原始 ID 和逐资源请求头。脚本不会持有 UI 对象 |
| Network、媒体传输 | URLSession、按源会话、WKWebView 登录、重定向、请求取消、图片解码和磁盘缓存。凭证按目的主机传递 |
| Playback、Reading、Audio | 视频进度由当前播放会话写入。阅读器报告章节与定位点，音频协调器处理切换、来电和锁屏归属 |
| Storage、Import、Sync | SQLite 模式升级、备份预览与事务导入、下载文件索引、同步冲突。应用通过同一资料库接口写历史 |
| Diagnostics | 按一次取址或一次内核装载记录耗时、错误类别和内核。换集与切核重新计时；导出时移除媒体路径、Cookie、查询串和令牌 |

一次点击播放应经过“选中章节 → 源解析 → 准备媒体与请求头 → 建立原生会话 → 首帧 → 进度推进”。UI 任务在主线程执行；解析、数据库批量导入、图片解码、磁盘读写分别限制并发。页面退出或快速换集要取消旧任务，并按会话代次丢弃迟到结果。首帧、缓冲、播放意图和可听声音分别验收，单靠时间轴走动不足以证明播放正常。

## 5. 源兼容是第一阶段的技术重点

首选验证现有 QuickJS 原生核心，把 Dart 宿主提供的能力逐项接入 Swift/C。清单涵盖二进制 HTTP、精确请求头、重定向最终地址、DOM、Base64、摘要、AES/RSA、压缩、按源存储、分页和设置。为每份样本记录使用的能力；遇到未实现的接口，向用户报告源名和缺失能力。源超时须能打断解释器，取消网络和释放资源。

| 格式 | 计划顺序 | 验证样本 |
| --- | --- | --- |
| LumeSource JS | V0.1 先覆盖首批视频源；V0.2 加入阅读类样本 | 普通 HLS、签名或加密、依赖 Referer、登录后可见、图片需解码、正文和音频；每种明确实际通过的脚本版本 |
| Kazumi、TVBox 数据配置、直播列表、T4/RPC | 后续按常用清单排优先级，先评估规则与远端接口 | 搜索、选线、选集、播放和失败提示。区分配置文件、远端服务和需要执行代码的 Spider |
| 猫源、Node、多文件 JS、Rex | 在模块加载、相对路径、缓存和隔离通过后启用 | ESM/CommonJS、多文件包、经典明文 Widget；加密 Widget 单列可行性，不承诺解密能力 |
| Python Spider、依赖原生扩展的包 | 独立验证运行环境、签名和发布方式，再排入版本 | 固定 ZIP、缺依赖、超时和异常退出；Java/DEX 类需求单列外部服务依赖 |

私有订阅继续从授权 GitHub 接口读取清单和脚本。令牌进钥匙串；下载完成且校验成功后再替换已装版本，失败保留可用副本。发布仍由现有源仓库和电脑端工具负责。建立两层验收：固定响应回放用于比较新旧宿主语义；用户常用真源抽样验证封面、分类差异、登录、选集、播放分片或正文。网络 403、签名过期和解析错误分别归类。

## 6. 旧数据怎样带过来

建议以用户手动“旧 App 导出 → 文件 → 新 App 导入”为第一条路径。现有 `lumebox-configuration` 写出 v2，恢复入口识别 v1/v2，并支持带密码的备份。先生成脱敏的两代备份、带密码备份和损坏样本，逐字段确定覆盖面。[现有备份实现](../lib/core/session/configuration_backup.dart) · [板块定义](../lib/core/session/section.dart) · [阅读库表](../lib/core/reading/reading_store.dart)

| 数据 | 新项目建议 |
| --- | --- |
| 源与设置 | 保留原 ID、板块、域名、源级偏好和启停状态。暂不支持的源保留记录，标记需要对应运行时 |
| 收藏、历史、逐集进度、书签 | 按原身份去重。进度冲突预览两边更新时间，默认取较新有效记录；完成状态、零进度、同书不同源单独测试 |
| 登录态、私有订阅令牌、服务凭证 | 新 App 提供重新授权入口。检查备份字段，遮盖敏感配置，避免凭证流入诊断和通用同步 |
| 下载、封面和缓存 | 清点备份实际携带的文件。可重建缓存按需重拉；旧沙盒内离线正文或视频若无导出能力，在迁移报告明确列出，另排文件导出与校验 |
| iCloud | 单独的同步命名空间或版本，明确删除记录和冲突规则。跨两设备验证后再开放写入 |

导入先解密、检查格式与空间，再展示各板块条数、冲突及跳过原因。导入中使用暂存区和数据库事务，文件与索引都就绪后才提交；保存新 App 导入前的恢复点。验收覆盖重复导入、密码错误、中途退出、空间不足和回滚。回到旧 App 可继续旧进度；新 App 此后新增的记录，需另行设计反向导出才能回流。

## 7. 里程碑、投入与依赖

以下按 **一名熟悉 Swift 与现有代码的主开发全职投入**估算，用户每阶段提供一次真机验收。数字是人周，顺序实施时可近似作日历周参考。预算包含实现、针对性验证与修复，不含等待签名、外部服务恢复、审核或新增需求。首阶段结束后用实测重估。

| 阶段 | 投入 | 可交付结果 | 进入下一阶段的依据 |
| --- | ---: | --- | --- |
| M0 可行性 | 1–2 | 并排安装的空壳、一个真实 JS 源、脱离 Flutter 的双内核测试页、一份旧备份解析报告 | 真机能取到媒体、出图出声；可打断死循环；已知备份字段有映射 |
| M1 源与资料库 | 2–3 | 私有订阅、检索、分页、源设置、作品与章节模型、SQLite、错误诊断 | 代表性源的固定样本回放通过，断网更新仍能使用已装版本 |
| M2 视频试用 | 2–4 | 原生列表、详情、选集、播放、换线、收藏、续看、视频数据迁移；首个日用试装包 | 完成第 1 节的全链路，在用户设备验收两内核与旧备份 |
| M3 阅读与音频 | 4–7 | 漫画、图集、小说、有声书、基础离线与定位恢复 | 各类型至少一部真实作品，离线重开可读，视频与朗读切换无串音 |
| M4 替代旧版前的收尾 | 3–6 | 完整迁移清单、下载恢复、隐私与诊断、选定的高频兼容格式、发布与回滚演练 | 用户常用清单逐项签收，待补能力可见，旧版数据可找回 |

**首个视频试用版约 5–9 人周，完成上述基础范围约 12–22 人周。** 全量 Python/Node 生态、公共弹幕、自动片头识别、OCR/翻译、超分、云同步和 iPad 专用布局按独立功能估算。预算以“人周 × 实际投入成本”加测试设备、签名和按需 macOS CI 计算。Windows 可承担源码与样本整理；iOS 编译需可用的 Mac/Xcode，设备方向、音频及后台行为需要 iPhone。若只有远程 Mac，应给设备安装和收集诊断安排固定时间。

## 8. 怎么判断原生重做值得继续

| 测项 | 建议验收方式 |
| --- | --- |
| 启动与浏览 | 相同设备、同一批缓存和封面测旧版与新版。冷启动到首屏可操作、滚动帧耗时和图片峰值内存分别记录。建议目标为本地书架冷启 P95 ≤ 2 秒；M0 实测后校准 |
| 播放 | 本地受控 MP4/HLS 分别测每内核至少 20 次的装载到首帧中位数与 P95，初始目标 P95 ≤ 2 秒；真实 CDN 另报取址、首字节和首帧。在真机横竖屏检查文字方向、切核保留进度、暂停、来电和退出 |
| 稳定性 | 连续快速切集／切核 20 次，检查过期声音和旧画面；持续播放 30 分钟后退出，用 Instruments 查看反复进出后仍存活的引擎、任务和内存趋势 |
| 阅读与音频 | 大图章节连续翻页、长章节重排、旋转后续读，记录掉帧和内存告警。离线、锁屏、耳机拔出、来电和切换到视频各走一次 |
| 数据 | 对照备份逐板块核对数量及抽样内容，同作品不同源不串进度；重复导入无重复条目，失败后原记录一致 |
| 无障碍与隐私 | 最大常用字号、VoiceOver、减少动态效果、减少透明度下完成核心流程。无痕观看后重开检查历史，核查导出包脱敏结果 |

日常修改按范围选择验证。文档检查引用和一致性；源宿主改动运行相关回放；数据库改动跑迁移样本；播放器改动跑对应设备或模拟器样本。用户需要安装包或里程碑交付时再走签名、归档和安装检查。保存版本、提交、机型、系统与样本编号，以便用户报告问题时能重现。

## 9. 风险、发布与评审选择

| 风险或早期信号 | 处理方式及其对范围的影响 |
| --- | --- |
| 普通 JS 源能列出作品，加密或多文件源失败 | 按能力拆分兼容矩阵；首包公开已验收格式，优先补用户最常用的失败样本 |
| 播放器脱离 Flutter 后丢失请求头、缓存或历史 | M0 用含复杂 Cookie 的受保护样本和慢分片服务验证；在端到端通路稳定前控制 UI 扩展 |
| 播放画面正常但 GPU 方向、后台音频或画中画失效 | 真机专项验收；明确每个内核支持的功能，仅启用已验证的入口 |
| 新旧 App 同时使用导致数据冲突 | 使用独立存储和同步版本，保留旧备份，以导入报告和恢复点处理差异 |
| 解释器、编解码库、模型资源拖大安装包或影响分发 | 锁定依赖版本与校验值，记录许可证及二进制来源，按版本测包体。阶段一先决定安装渠道 |
| 待迁移功能持续增加 | M0 冻结用户的常用源与任务清单，每个新增需求写明挤占哪个阶段，按可使用的版本交付 |

个人签名试用可沿用熟悉的设备安装流程。若目标包含公开 App Store，M0 就应核对动态脚本与解释器、内容来源与授权、可下载内容和隐私披露，特别是审核条款 2.5.2、1.1 和 5.2。两种发布目标会改变首版可提供的源类型和测试范围。[Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)

**评审时最值得决定的三件事**

1. **首包用来做什么？** 建议先要一个每天能看视频的包。若漫画或听书同样优先，把常用作品列入 M0，并把对应阅读能力提前到 M2。
2. **哪些源和数据必须带走？** 选 5–10 个日常使用的源，加一份脱敏备份和典型离线内容。若必选源依赖 Python 或 Node，应在 M0 先验证该运行时，并重估视频试用版工期。
3. **准备怎样安装和发布？** 建议先在自己的 iPhone 上并排试用。确定渠道后，再定 Bundle ID、签名、凭证策略、首批机型和正式产品名。

评审通过后，先交付 M0 的技术样机：在 iOS 26 真机跑通一个现有源、播放同一集视频，并给出旧备份字段对照。M2 再把订阅、浏览、逐集续播和数据导入连成可日用的试装包。
