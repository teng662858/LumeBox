# 懂片帝源（`video/dongpiandi.js`）

2026-11-03。站点：懂片帝 / 懂片帝AI（`https://dongpiandi.ai`，标题「懂片帝AI - 懂片AI找片、片单与播放」）。
定位是**AI 找片 + 片单 + 播放**的聚合前端：自己不做片库，把各家聚合资源站（红牛、新浪、极速、豪华、
ikun、无敌、魔都、西瓜…）和官方 CDN（bytevod / bytetos）的线路编排到一部作品上。

形态是 **React SPA + 同源 `/v1/*` JSON 接口**：首页 HTML 只有 4 KB，`<div id="root">` 之外没有内容，
所有数据都得走接口。站点前面是 CloudFront，实测直连可开（`network: "direct"`）。

## 一、签名（不通这一关什么都取不到）

每个 `/v1/*` 请求都要三个头，少一个就回
`401 {"error":{"code":"invalid_request_signature","message":"Missing request signature."}}`：

| 头 | 值 |
|---|---|
| `x-ai-movie-timestamp` | `Date.now()` 毫秒 |
| `x-ai-movie-nonce` | 16 字节随机 hex（32 字符） |
| `x-ai-movie-signature` | `HMAC-SHA256(SIGN_KEY, msg)` 的 hex |

```
msg = METHOD + "\n" + pathname + search + "\n" + timestamp + "\n" + nonce
SIGN_KEY = 8b9a908a05eac640e1ee06f52acaa741bfe4ba9e004eeffdbeb635e532e06666
```

- 算法出自 `/assets/movie-card-runtime-*.js` 的 `Aa` / `Ta`（key 是模块里的 `Jo="…"`）。
- **只校验这三个头**：`x-ai-movie-client-name` / `client-version` / `build-version` /
  `protocol-version` / `site-host` 都不填也能过 —— 站点换前端版本不影响本源，不用跟着改版本号。
- 签名后的 `pathname + search` 必须与真实请求路径逐字一致，所以源里所有查询参数都自己
  `encodeURIComponent`，不让宿主做二次编码。
- 设备时钟偏差会让签名失真：源里遇到 `invalid_request_signature` 时按响应 `Date` 头校正
  `clockSkew` 再重试一次（只校一次，避免死循环）。
- 站点换 key 时：把新 `main-*.js` 里的 `Jo="…"` 抄进源的 `SIGN_KEY` 即可。

## 二、接口（全部 GET/POST JSON）

| 用途 | 路径 | 关键参数 |
|---|---|---|
| 首页板块 | `/v1/feed/home` | `cursor`（预览只回 8 个板块，`meta.total_sections=11`） |
| 列表 / 搜索 / 榜单 | `/v1/browse/catalog` | `q` / `kind` / `genre` / `area` / `language` / `year` / `sort` / `hot_list_key` / `page` / `limit≤20` |
| 分类与筛选表 | `/v1/runtime/bootstrap` | 读 `catalog_ui.catalogs[].rows[].options[].params` |
| 详情 + 分集 | `/v1/catalog/{id}` | 返回 `episodes[]`，每条带 `token` |
| 线路表 | `/v1/playback/resolve/{token}` | 返回 `line_options[]`（本片 13–32 条） |
| 票券换址 | `POST /v1/playback/resolve-line?view=compact` | body `{ticket}`，成功 201 |
| 游客会话 | `POST /v1/users/anonymous` | 本源默认不用（票券线路匿名也能换） |

`limit` 上限 20，传更大也只会回 20 条；分页用 `page`（`pagination.has_more` 判「还有」）。

## 三、分类 / 筛选 / 排序（v1.3.0 补全，2026-11-03 参数矩阵实测）

### 分类 17 个（id 就是站点查询串）

| 组 | 分类 id |
|---|---|
| 混合 | `all`（最近更新，forced `sort=updated_desc`） |
| 类型 | `kind=movie`、`kind=series`、`kind=anime`、`kind=variety`、`kind=short_drama`、`kind=documentary`、`kind=sports` |
| 热播 | `sort=trending&window=day`（今日）、`sort=trending&window=week`（本周） |
| 榜单 | `hot_list_key` = `tv_domestic` / `tv_korean` / `tv_japanese` / `tv_american` / `movie_hot` / `movie_high_score` / `movie_nowplaying` |

- kind 分类默认显式带 `sort=heat_desc`（bootstrap 里 5 个 kind 的 `default_sort` 都是它）。
  实测「不带 sort」时站点其实按最新出，所以不显式给就变成和「最近更新」一样的首屏。
- 17 个分类两两对比：**15 个首条唯一**，重复的两个是「今日热播 / 本周热播」（榜首都是《嫁金钗》，
  站点数据本身重合，第二页起就不同：日榜第 2 是《尚公主》，周榜第 2 是《小城良方》）。
- 首页板块的「更多」用 `section.browse.params` 转成同一套编码（丢掉 `page`/`limit`），
  点进去就是普通列表分页。

### 筛选组（按分类给不同的表）

| 分类 | 组 | 来源 |
|---|---|---|
| movie / series / anime / variety / short_drama | 分类 / 地区 / 语言 / 年份 / 排序 | `/v1/runtime/bootstrap` 的 `catalog_ui`（选项 18 / 29 / 18 / 10 / 76 个） |
| documentary / sports | 分类 / 地区 / 语言 / 年份 / 排序 | 本地表（bootstrap 没有这两个 kind，但实测参数同样生效；genre 值从片库反查：纪录片/音乐/历史/犯罪/传记…、体育/体育赛事） |
| all / 今日热播 / 本周热播 | 地区 / 语言 / 年份 / 排序 | 通用表（实测「不带 kind」时 area / year / genre 照样生效） |
| 7 个榜单 | 无 | 实测榜单会丢掉附加参数（`hot_list_key + area` 的 area 不生效，`+ sort` 反而把榜单顶掉） |

选项 id 里编码站点真实参数，`|` 表示多参数：`genre:喜剧`、`area:中国大陆`、
`year:2026`、`year_lte:2024`、`year_gte:1990|year_lte:1999`、`sort:heat_desc`。

**多选支持情况（实测）**：

| 组 | 多选 | 证据 |
|---|---|---|
| 地区 `area` | ✅ 支持逗号多值 | `area=中国大陆,中国香港` 返回混有两地的结果 |
| 分类 `genre` | ❌ | `genre=喜剧,爱情` → 0 条 |
| 语言 `language` | ❌ | `language=国语,粤语` → 0 条 |
| 年份 | ❌ | 区间靠 `year_gte`/`year_lte` 两个键 |

源里 `parseFilterGroup` 只对 `area` 做拼接，其它组取第一个。

### 排序

站点 `sort` 只认 `updated_desc` / `heat_desc`（`sort=whatever` 被直接丢掉），
另有榜单专用的 `sort=trending` + `window=day|week`。筛选里的「排序」组选完会覆盖分类默认值
（实测 `kind=movie` 默认《空枪》→ 选「最新」变《半山腰的索玛花》）。

### 没有的维度（实测被静默忽略，不做假声明）

`rating_gte` / `score_gte` / `duration_lte` / `is_finished` / `status` / `free` /
`playable_only` / `actor` / `channel` / `region` / `lang` / `sort_by` / `window(单独)` —— 全部无效；
短剧的「状态」「形式」两行站点自己标了 `enabled:false`，按规矩跳过。

## 四、播放（两层线路，默认不碰额度）

`line_options[]` 里两种线路：

1. `resolve_mode:"direct"` + `url` 本来就是 `http(s)://…m3u8|mp4`（第三方聚合资源站，占绝大多数，
   实测 200/206 + `#EXTM3U`）→ **不需要登录、不扣额度**，本源默认走这条。
2. `resolve://<ticket>`（官方 1080P/4K、bytevod/bytetos）→ 要 `POST /v1/playback/resolve-line`
   换真实地址，按站点词元计费；默认只在直链一条都没有时才兜底。

**为什么不逐条探活**：App 单次调用预算 3–5 秒，而聚合资源站的 CDN 里总有一两条已经挂掉、
要等宿主 6 秒超时才回（实测某集 4 条串行探活把 `content` 拖到 16 秒，直接判超时）。
所以改成「按实测稳定性排序 + 一次 resolve 直接给地址」：

- 权重 = 站点 `preference_weight` + 资源站稳定性修正（hongniu/xinlang/jszy/hhzy/ikun/subo 稳定 +300，
  ffzy/suoni/niuniu 常挂 −260，dbzy/maotai/jinying 偏低）；官方 mp4 直链本来权重最高。
- 排序后前 5 条进 `qualities`（label 用资源站名），默认播第一条，别的线路用户可在播放器里切。
- 正常情况 `content` 只要 **0.2–0.9 秒**，不会再撞预算。

## 四·二、账号要不要填（2026-11-03 用真实账号实测）

结论先给：**不填也能用全部片库**。

| 场景 | 登录前 | 登录后 |
|---|---|---|
| 线路表（嫁金钗第 1 集） | 34 条（25 直链 + 9 官方票券） | **完全一致**：provider / 权重 / `token_scenario` 逐条相同 |
| 4K 票券（`新4K-限时等级专属`） | `resolve-line` → 201 + 真地址 | 同 |
| 4K 海外（`4K海外-官方C`） | 201 + 真地址 | 同 |
| 1080P 官方 S/V/B | 201 + 真地址 | 同 |
| `/v1/users/me/quota` | 401 `User session is required` | 200 |
| `/v1/midnight-theater/*` | 401 `midnight_session_required` | 403 `midnight_confirmation_required`（要先确认 18+） |

所以登录多出来的只有**站内那套账号功能**（每日词元额度、收藏、播放历史、午夜剧场），
对「能不能看、能不能换 4K」没有任何影响。本源把账号做成**可选**：

- **登入接口**：`POST /v1/users/password/login`，body `{account, password}`（字段名是 `account`
  不是 `username`，传错回 400 `validation_error`；登录不要验证码，注册才要 `captcha`）。
  成功 201，`Set-Cookie` 里给 `ai_movie_session=ums2_…`（HttpOnly，一年有效）。
  同一条响应里还会先塞几个 `Max-Age=0` 的空 cookie 覆盖旧值，所以取 cookie 要按
  `ai_movie_session=ums2_` 前缀匹配，不能取最后一条。
- **会话**存 `LumeSource.fs`（`session.json`，按账号隔离，换账号自动失效），
  下次调用直接复用；401 时清掉重登一次。
- **登录失败不阻塞播放**：密码错只写一条 `login_fail.json`（含凭据指纹 + 30 分钟 TTL），
  期间不再白试登录，票券照样按匿名身份换得到地址。
- **线路偏好**（`lineMode`）：`direct`（默认，直链优先，免费）/ `official`（先换官方票券，
  画质更好、扣词元，失败回落直链并把直链一起塞进 `qualities`）。
- **设置页两个动作**：`检查账号与额度`（强制登录一次，显示昵称 / 等级 / 今日词元用量）、
  `退出站点登录`（清会话）。实测输出：

```
账号：teng233（林间小太阳2017）
等级：练气1层（member）
今日词元：已用 0 / 上限 100 万，剩余 100 万
额度重置：2026-11-03T16:00:00.000Z
```

`/v1/users/me/quota` 关键字段：`used_tokens` / `limit_tokens` / `remaining_tokens` /
`reset_at`，另有 `level_benefits`（含 `official_line`：同一影片只计一次词元、不限下载投屏）
与 `economy.service_estimates`（官方蓝光约 66 次）。

## 四·三、午夜剧场（v1.4.0 已接入成分类，结构按前端契约、待真实响应复验）

站点那套「AI 现生成今晚片单」的玩法，已接成第 18 个分类 `midnight`，走的是
`discovery → play → timeline 展开成分段` 这条路，**不是**走 catalog。

### 数据流

```
GET  /v1/midnight-theater/access
       200 = 有资格；403 按 code 翻人话（session / confirmation / not_eligible / youth_mode / disabled）
GET  /v1/midnight-theater/discovery?history_limit=8&watching_limit=8[&history_cursor=&watching_limit=0]
       → { history[], watching[], history_next_cursor, history_has_more,
           watching_next_cursor, watching_has_more }
       卡片：{ id, title, cover, author?, created_at?, cost? }
POST /v1/midnight-theater/playlists/{id}/play   { play_request_id }
POST /v1/midnight-theater/playlists/random/play { play_request_id }
POST /v1/midnight-theater/top/play              { play_request_id }   ← 今日热门片单
       → { playlist_id,
           materials: { items: [ { title, cover_url, duration,
                                    media_sources: [ { url, format, width, height } ],
                                    sprite?, collection_target? } ] },
           timeline: { total_duration,
                       segments: [ { material_index, media_source_index,
                                      timeline_start, timeline_end, source_start, source_end } ] } }
POST /v1/midnight-theater/playlists            （生成：mode/text/matching_mode/image_token/
                                                age_confirmed/generation_id/session_id/count/device_id）
```

### 本源怎么接

- **分类「午夜剧场」**：`list()` 走 `discovery`，第 1 页把「大家都在看」（watching）和
  「我生成过的」（history）合并去重，第 2 页起只用 `history_cursor` 续翻（游标存 `fs`）。
  条目 id 带 `mt:` 前缀。
- **`detail()`**：片单没有独立详情接口，用 list 时缓存的标题/封面；缓存没命中就返回可播放占位。
- **`chapters()`**：一次 `play` 换回整条时间线，把每个 `timeline.segment` 展开成一个章节
  （标题取 `materials.items[].title`），一条片单也能顺着看完。
- **`content()`**：按章节索引取该段的 `media_sources[].url`（m3u8/mp4），带 UA。
  `play` 结果缓存 10 分钟，避免重复扣词元。
- **`filters()`**：0 组（片单没有可筛维度）。

### 验证到哪一步（诚实说明）

| 项 | 结果 |
|---|---|
| `play_request_id` 必须标准 UUID v4 | **实测**：纯随机 hex → `400 play_request_id: Invalid UUID`；改成 8-4-4-12 且第三段首字符 `4`、第四段首字符 `8/9/a/b` → 400 消失，变成 403 资格拦截 |
| 播放接口路径与 body 结构 | **实测通过校验**：`random/play`、`top/play`、`playlists/{id}/play` 三个都从「400 格式错」变成「403 not_eligible」，说明请求形状被服务端接受 |
| 匿名 / 未登录 | **实测**：分类列表回「午夜剧场要站点账号：请在『源设置 → 账号登入』里填账号密码」 |
| 没资格账号 | **实测**：回「午夜剧场打不开：账号暂不符合开放条件（站点按等级/活跃度灰度，练气1层实测不开放）（midnight_theater_not_eligible）」 |
| **discovery / play 的响应结构** | **未在真实响应上验证** —— 账号无资格，两个接口都 403，拿不到样本；结构全部来自 `/assets/MidnightTheaterRoute-*.js` 的消费代码（`v.data.history/watching/*_next_cursor`、`oe.playlist_id`、`e.timeline.segments`、`e.materials.items[].media_sources[].url`）。解析全程防御式：字段缺了就降级/跳过，不编造 |

换句话说：**请求侧已经打通并验证，响应侧等账号资格放开后要拿一真实片单复验一次**。
资格到位前，分类会明确告诉用户为什么打不开，不会静默返回空。

## 五、交付形态

- 板块 `video`；`contentCategory: "movie"`（与同架构的看剧AI 源一致：主站是综合影视聚合，
  成人内容只在站内分类里出现，不是成人专站）。
- 章节 id 用站点的 episode token（`t:<token>` 前缀），`content` 直接拿它换流，不需要再请求详情。
- 单集内容（电影/短剧）章节标题用站点 `remarks`（「高清」「全1集」），多集用 `第N集`。
- `detail()` 把演员/导演/类型拼进简介，封面用 `poster_url`（站点走 `gimg0.baidu.com` 代理，
  直接 200 + `image/webp`，不需要额外请求头）。

## 七、限制

- 接口依赖站点签名 key；站点大改前端（换 key）时本源要跟一次 `SIGN_KEY`。
- 「午夜剧场」已接成分类（详见四·三）：请求侧验证到「格式通过、被资格拦下」，
  但 discovery / play 的**响应结构还没有真实样本**（账号练气1层没资格，两个接口都 403），
  等资格放开要拿一条真实片单复验一次；期间源会给明确的可读原因，不会静默返回空。
- 午夜剧场播放按次扣站点词元（站点自报「高级剧场每次 50 万」量级），本源把 `play`
  结果缓存 10 分钟，同一条片单反复拉章节不会再扣。
- 只有「官方线路优先」或直链全挂时才消耗站点词元（账号等级 1 = 每日 100 万）。
- **个别条目站点自己就没线路**：例如《爱·回家之三代同糖》只挂暴风资源 3 条，实测
  3/3 回 404，`resolve` 里也没有官方票券 —— 这种条目本源会把第一条直链交出去让播放器
  自己报错（探活已经确认过它不可用）。`lume-source-check` 默认取「最近更新」首条，
  撞上这类条目会 FAIL，换 `--category` 即 PASS，属于站点数据问题而非源。
- 站点是 CloudFront 分发，若某地线路被拦在「源设置 → 换网址」里填可用域名即可（脚本按
  `LumeSource.config.domain` 拼地址）。
