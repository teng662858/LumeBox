## 一、怎么把 CF 站的内容拿到手（本次新方法）

之前「做不了」的真正原因是：`node`/`dart` 直接请求只会拿到 403 挑战页，没有真实 HTML 就没法写解析、
更没法验收。这次用 **Chrome + CDP** 打开站点，让挑战在真浏览器里跑完，再 `Runtime.evaluate`
把 `document.documentElement.outerHTML` 取出来：

- headless Chrome 对 `/book/`、`/novels/class/` 这类页面能过，但 `/txt/`（正文页）反复卡在
  「请稍候…」；
- 换成**有头 Chrome**（同一个 `--user-data-dir` 思路，CDP 端口 9223）后 `/txt/` 也过了，
  拿到正文 HTML（GBK，31 KB）；
- 抓完页面顺手拿到了 `cf_clearance` 等 Cookie。

## 三、源里怎么处理 CF 与 GBK

- **CF**：所有请求统一走 `fetchHtml()`，403 / 503 / 521 或响应体里出现 `Just a moment`、`cf-chl-`、
  「请稍候」就抛 `NEED_WEBVIEW_VERIFY：…`。App 打开网页视图让用户本人过一次校验，
  `cf_clearance` 按站点保存复用——这就是「App 能过 CF」的正规用法，不需要绕过任何校验。
- **GBK**：站点 `charset=gbk`。App 侧 `SourceTextDecoder` 会从响应头/前 4 KB 里认出 charset，
  iOS 走原生 `decodeText(gb18030)` 通道，正文正常；桌面/Node 打测器退回 `utf8` 会看到乱码，
  这是工具限制，不是源的问题。

## 五、次元姬（ciyuanji.com）的卡点：不是 CF，是「书的地址是密文」

这次也把次元姬重新挖了一遍，结论比上次更具体：

1. **不是被墙/被 CF 挡**：`m.ciyuanji.com` 和 `www.ciyuanji.com` 都能直连 200（Next.js SSR）。
2. **书详情页的 URL 是密文**：`/bookDetails?params=pXk5sagxDKLDoK7nE8zIxgn3TIpv%2FkTv`
   —— `params` base64 解出来是 24 字节二进制，不是数字 id；
3. **这个 URL 直接打开只会落回首页外壳**：`__NEXT_DATA__` 里 `pageProps` 只有
   `recommendRegionList`（推荐位）/`classifyList`（分类），**没有书的内容**；浏览器里打开也没有任何
   发往书籍接口的 XHR（真机抓包同样为零）；
4. **API 基址已知但端点未知**：`_app` chunk 里写着
   `https://www.ciyuanji.com/api/pc/cms`（另有 `prep.ciyuanji.com/api/pc/cms`），
   但 29 个 chunk 里没有任何写死的端点路径（都是运行时拼的），`/api/pc/cms` 下的常见路径 404；
5. 各页 chunk 能拿到（`/_next/static/chunks/…` 200），分类树也能从 `m.ciyuanji.com/category`
   的 `classifyList` 读出（classifyId 10101…），所以**差的只有「书目接口 + params 的加密方式」**。

要我把它做完，最省事的两条路（任选其一）：
- 你在 App/浏览器里点开**任意一本书**，把地址栏那条 `bookDetails?params=…`（或阅读页 URL）发我
  —— 我用同一个浏览器会话重放它、抓 XHR，就能拿到端点与参数结构；
- 或者给我一个能打开书页的登录态（`document.cookie`），我直接在会话里调接口。
