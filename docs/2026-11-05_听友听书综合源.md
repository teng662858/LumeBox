# 2026-11-05 听友听书（tingyou.fm）综合源

`tingyou_video`：听友听书（`https://www.tingyou.fm/listening`，同内容域名 `tingyou.fm` / `www.tingyou.fm` /
`fmfm.tingyou.fm`，三者都 302 到 `/listening`）**综合源**：左边「听书」（有声小说 / 评书 / 榜单，
mp3 直链）、右边「影视」（电影 / 连续剧 / 动漫 / 短剧 / 综艺，HLS）。已在源仓库
`metadata/mixed-sources.json` 登记，生成综合订阅，同时保留在视频订阅里。

站点是 Nuxt3 SSR 外壳，数据全走接口；**两套接口完全不同**，下面按通道记。

## 一、听书通道（明文 JSON）

接口基址 `https://appp.fdhtbz.cn/api`（另有 `ffggewvge.dasfrvvbbhhafdgserqw.cc/api`、
`fsfggqwewrr.dsafasfvvaaee.cc/api` 两个备用域名），全部走 `/h5/listening/*`：

| 用途 | 请求 | 说明 |
|---|---|---|
| 筛选表 | `GET /h5/listening/filters` | `sorts[4]` + `categories[2]`（有声小说 26 个题材、评书 17 个） |
| 分类列表 | `GET /h5/listening/category?category=&type=&sort=&page=N` | 固定 20 条/页，回 `{data,page,pages}` |
| 榜单 | `GET /h5/listening/rank?section=&page=N` | `hot` / `recommend` / `latest`，30 条/页 |
| 专辑 | `GET /h5/listening/album/{id}` | `synopsis` / `count` / `cat` / `type` / `cover_url` |
| 目录 | `GET /h5/listening/chapters/{id}` | **一次给全**，实测《剑来》5329 章 558 KB |
| 播放 | `POST /h5/listening/play` | body `{album_id, chapter_idx}` → `{play_url}`，mp3 实测 206 + `audio/mpeg` |
| 搜索 | `POST /h5/listening/search` | body `{keyword, page}` → `{results, has_more}` |

**必须带的头**：`x-listening-session`（v4 UUID，脚本生成后存 fs）、`x-listening-timezone`、
以及 `Origin` / `Referer`——**缺 Origin/Referer 时接口直接 404**（第一版就栽在这，别当站点改版）。

分类参数名是真机抓包确认的：`category=2`（有声小说）/ `1`（评书）、`type=46`（玄幻奇幻）…
一开始试的 `cat` / `cat_id` / `category_id` 全被静默忽略（返回不分类的结果，看起来像「筛选没生效」）。

## 二、影视通道（请求与响应全加密）

所有操作都走同一个 `POST /web/v1/tv/call`，body 是 `{operation, params, query, payload?, idempotency_key?}`，
但**整段加密**：

1. 请求体 = `AES-256-CBC(PKCS7)` 加密的 JSON（含 `device_id/brand/model/appVer/osVer/timestamp`），
   结果是 **base64 文本**，直接当 body 发（`Content-Type: application/x-www-form-urlencoded`）；
2. `X-Post-Signature` = `base64(HMAC-SHA256(8 字节固定密钥, 上面那段 base64 文本))`；
   `X-Device-Id` = 安装 UUID（JSON 里的 `device_id` 也是它）；
3. 响应体 = `base64(AES-256-CBC(同一 key/iv))` → JSON。

密钥是前端常量（`sources/video/tingyou.js` 顶部三行）：

```
AES-256 key 11059a4c989dd9d4837778b013d164baa0ad4d7b0076e722369f6f085814293f
IV          dd3ea319024c649d2ebcd1bda551a307
HMAC key    51c5b55800a7efd1（8 字节）
```

签名错时服务端回**加密的** `{"code":400,"message":"missing signature"}`——所以「能解开但报错」是这个原因，不是 key 错了。

用到的 operation（都在站点前端的公开集合里）：`pages.list` / `pages.tab` / `catalog.works` /
`catalog.collection_items` / `catalog.work` / `catalog.episodes` / `catalog.work_filters` /
`search.works` / `playback.lines` / `playback.session`。

**播放要账号**：匿名调 `playback.lines` / `playback.session` 一律 `401 需要登录`。站点 web 端自己会静默领一个
游客账号（`POST /web/user/register/temp`，body 里 `content` 为空串），本源照做：首次自动注册、token 存
`fs`（3 天 TTL）、401 时重领一次。拿到 token 后 `playback.session` 回 `manifest_url`
（`https://api-preview.toulaopao.cc/play/<EdDSA JWT>/N/v1/objects/xx/<output>/master.m3u8`），
实测 200 + `application/vnd.apple.mpegurl`。线路表里 `is_vip: true` 的线路不取。

**分页是游标**：`catalog.works` 给 `page=` 会回 `400 电视请求参数无效`（`sort` 给错值才是 `422 校验不通过`）。
所以源里用 `next_cursor` 链：每翻一页记下下一页游标（存 `fs`），顺序翻页 1 次请求/页；
冷启动越级翻页最多自动补 3 跳，再远就明确报「只能从第 1 页顺序往后翻」。

认可的筛选键（来自 `catalog.work_filters`，实测叠加生效）：`kind`（movie/series/variety/anime/short）、
`area`、`year`、`tag`（哈希）、`serial_state`（ongoing/completed）、`sort`
（`updated_desc` / `published_desc` / `popularity_desc`）。

## 三、接口域名会轮换，脚本自己找

站方用一份加密的「启动头」下发当前 `api_hosts`：

```
GET https://toudnbbaa.tou1laopao.cc/api/startup-head/h5api.dat
```

字节布局 `[密文][key 32B][iv 16B]`，`AES-256-CBC(PKCS7)`（WebCrypto 一定补位，实测尾部 `07×7`）。
解出来是 `{api_hosts:[...], next_heads:[...], api_host_contracts:[...]}`。本源解头拿域名再逐个探活
（`/time/seconds` → `{"code":0}`），成功就把基址缓存 6 小时；解不出或全探不通时退回内置的三个域名。

实测这台机器上 `appp.fdhtbz.cn` 会**阶段性 404**（同一时刻另两个域名 200），所以「探活 + 换台」不是保险，是必需。
「头解出来的域名」这条路径做过对照验证：把内置三个域名全改成 `invalid-*.example` 后，源照样跑通。

## 四、封面：站方自研的 TVIMAGE1 信封（要 App 侧解码）

听书封面是普通 `file.tingyou8.vip/pic/*.jpg|gif`；影视封面全是 `.tvi`，报文体是：

```
'TVIMAGE1' | uint32 头长度 | JSON 头 | AES-256-GCM 密文 + 16B tag
```

JSON 头里有 `nonce` / `wrapped_key` / `plaintext_sha256` / `asset_id` / `role`，其中
`wrapped_key = key XOR SHA-256('tv.image-envelope/v3/wrapped-key\0' + nonce + 摘要 + 0 + asset_id + 0 + role)`，
并且 **JSON 头本身是 GCM 的 AAD**。没有固定密钥、也没有固定 IV，所以老的
`lume-enc://` 那套表示不了。

因此 App 侧新增一种图片编码 `x-lume-image-encoding: tvimage1`
（`lib/core/reading/image_bytes_decoder.dart` 的 `_decodeTvImageEnvelope`，pointycastle 的 `GCMBlockCipher` + AAD）。
源里只给影视条目挂 `coverHeaders: {'x-lume-image-encoding': 'tvimage1'}`，图片本身仍走原生管线下载。

## 五、验证结果（本机）

```
node tools/lume-source-check.mjs sources/video/tingyou.js
  [PASS] home 1898ms / categories 58 个 / list 30 条 / detail ok
         chapters 5329 / content kind=audio（mp3）
node tools/lume-source-check.mjs sources/video/tingyou.js --category "v:kind:movie"
  list 24 条 / detail ok / chapters 1（HD）/ content kind=video
  playable: 200 application/vnd.apple.mpegurl bytes=72785 sample="#EXTM3U ..."
node tools/lume-source-check.mjs sources/video/tingyou.js --keyword "遮天"
  search 15 条（听书 + 影视合并）
```

- 听书 mp3 直链：`206 audio/mpeg`；`chapter_idx` 越界（5330 > 5329）回 404。
- 影视 manifest：`200 application/vnd.apple.mpegurl`，清单里 `#EXT-X-KEY:METHOD=AES-128` 指向同域 key。
- 封面：听书 `image/gif|jpeg` 200；影视 `.tvi` 解码后 1,900,099 字节，`sha256=ddee8809…022`
  与头里的 `plaintext_sha256` **逐字相同**（`flutter test test/image_bytes_decoder_test.dart` 里
  有合成信封的往返用例，真实封面用临时用例单独核过）。
- 分类自测：58 个分类逐个跑 `list`，首条互不相同（听书的「连载榜 / 评书榜」与
  「最新上架 / 评书分类」逐条相同，所以**没有**重复声明成两个分类）。

## 六、限制

- 影视**播放需要游客账号**（脚本自动领，不需要手机号）；`is_vip` 线路不取，VIP 专享片只能看到详情。
- 影视分页是游标：只能从第 1 页顺序往后翻（越级最多自动补 3 跳）。
- 站点没有公开的「筛选」入口给听书，题材做成独立分类（26 + 17 个），排序由榜单承担。
- 接口域名会轮换，脚本已做解头 + 探活，但站方若同时换掉「头地址 + 三个域名」需要更新源。
- 影视封面依赖 App 新增的 `tvimage1` 解码；旧版 App 会显示占位图（不影响播放）。
